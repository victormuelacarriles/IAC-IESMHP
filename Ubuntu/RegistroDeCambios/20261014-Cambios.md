# Cambios 2026-10-14

## ~09:45 — `3-UneAlDominio.sh`: no abortar si el reloj está bien pero chrony no ha elegido fuente

**Síntoma (SMRD-00, Ubuntu 26.04 recién instalado)**: `3-UneAlDominio.sh` aborta en
el paso 3b con `[ERR] El reloj sigue SIN sincronizar (NTPSynchronized=no)`.
`chronyc sources -v`:

```
^- belgica1.iesmhp.local   4   6   377    49   -997ms[ -997ms] +/-  198ms
^? ntp-nts-*.canonical...  0   6     0     -   (x6, inalcanzables desde el aula)
```

El DC se alcanza (`Reach 377`) y el desfase es de **~1 s**, pero chrony lo marca
`-` (no combinado) y **no selecciona ninguna fuente** (`Reference ID 00000000`,
`Leap status: Not synchronised`). Así que `NTPSynchronized=no`, aunque para
Kerberos (<5 min) el reloj es perfectamente válido.

**Cambio**: en el paso 3b, si `NTPSynchronized=no`, plan B solo para chrony: se
lee `chronyc -n -c sources` y, si hay una muestra del NTP del dominio (`$NTP` de
`entornoAD.sh`) con `Reach≠0` y desfase medido `< 60 s`, se avisa y se continúa.
Si no la hay, se aborta igual que antes (para no dejar un objeto huérfano en la OU).
El mensaje final pasa de "Reloj sincronizado por NTP" a "Reloj válido para Kerberos".

**Pendiente (no tocado)**: aún no se sabe por qué chrony no elige el DC.
Sospechas: la selección de chrony con las fuentes **NTS** de Canonical que trae
26.04 (`authselectmode`), o el estado que anuncia el w32time del DC. Para
confirmarlo, en el equipo:

```
chronyc selectdata                       # letra de estado = motivo de no selección
chronyc ntpdata 10.0.1.48 | grep -Ei 'leap|stratum|root'
grep -rv '^\s*#' /etc/chrony/chrony.conf /etc/chrony/conf.d /etc/chrony/sources.d
```

Con esa salida se decidirá el arreglo de fondo en `tasks/main.yml` del rol
(p. ej. `authselectmode ignore` o desactivar las fuentes NTS en el aula).

**Resultado**: con el plan B, la unión de SMRD-00 **funciona** (confirmado por el
usuario).

## ~10:30 — Rol `preparaAD`: el reloj se valida por el desfase con el DC

Lleva al rol el mismo criterio que el plan B del script, para que la falsa bandera
no cueste tiempo ni dé avisos falsos.

- **`tasks/main.yml` (chrony)**: el `chronyc waitsync 30 0.05 0 1` (que con la
  falsa bandera esperaba siempre 30 s) pasa a ser un **sondeo** de hasta ~30 s
  (10×3 s) que **acaba en cuanto** el reloj está sincronizado **o** el desfase con
  el NTP del dominio (`chronyc -n -c sources`, columna 9, `Reach≠0`) es menor que
  `preparaad_desfase_max`. Devuelve `SYNC` | `DC <s>` | `SINDC`.
- **Salto de rescate (nuevo)**: si el DC responde pero el desfase es ≥ 60 s,
  para chrony, hace `chronyd -q -t 20 'server <ntp> iburst' 'maxdistance 16.0'`
  (sin leer `chrony.conf`, así que no le afectan las fuentes NTS) y vuelve a
  arrancar chrony. Después se vuelve a leer el estado (con otro `register`, porque
  si la tarea se salta pisaría la variable).
- **Veredicto único** `preparaad_reloj_ok` / `preparaad_reloj_detalle`.
- **Unión desatendida** (`preparaad_unir=true`): nuevo `fail` antes de
  `realm join` si el reloj no vale. Así no queda un objeto huérfano en la OU
  (antes solo lo protegía `3-UneAlDominio.sh`).
- **Resumen**: la línea "Reloj sincronizado por NTP: NO — Kerberos fallará…" (falsa
  en este caso) pasa a ser "Reloj válido para Kerberos: SÍ (sincronizado) / SÍ —
  desfase X s, falsa bandera / NO — …".
- **`defaults/main.yml`**: nueva `preparaad_desfase_max: 60`.
- **`utilesAD/3-UneAlDominio.sh`**: se mira el desfase con el DC **antes** del
  `makestep`+`waitsync` (antes se gastaban 30 s y luego se aceptaba igual).
- `CLAUDE.md` del rol: punto 3 (Reloj), tabla de variables y Estado/Notas.

Validado: el YAML se parsea, `bash -n` sale bien y el `awk` da el resultado
esperado con una línea CSV como la de SMRD-00. **Falta probarlo en un equipo**
(VM y aula, también sin monitor).
